# 動画アップロード機能 — 要件検討メモ（v0）

> 本書は動画アップロード機能について、要件定義前の検討経過をまとめたメモです。
> 決定事項と未決定事項を分けて記載し、次回の検討はここから再開します。
> （最終更新: 2026-08-13）

---

## 1. 背景・目的

- 現行の「家族のアルバム」は写真投稿のみ対応。動画も投稿できるようにしたい。
- 発端の懸念：動画は写真よりファイルサイズが大きく、ストレージ容量をすぐ圧迫するのではないか。
  - → 実際の空き容量を確認したところ、Raspberry Pi本番機の外付けSSDは 466GB中 使用197MB（1%未満）。
    現在の写真159枚・合計85MBに対し十分な余裕があり、動画を追加しても当面のストレージ枯渇リスクは低いことを確認済み。
  - ただし「際限なく大きい動画」が来るケースへの安全弁として、長さ・サイズ制限は引き続き設ける方針。

---

## 2. 決定事項

### 2.1 対応端末・ブラウザ
- 撮影・閲覧ともに **iPhone / iPad / Mac（Safari系ブラウザ）のみ** を想定する。
- iPhone上のChrome/Firefox/EdgeもOS制約により内部エンジンはSafariと同一（WebKit）のため、動画コーデック対応状況もSafariと同じ扱いでよい。
- Windows PCやAndroidでの閲覧は現時点ではスコープ外（将来必要になれば別途対応検討）。

### 2.2 動画フォーマット・変換方針
- iPhoneはHEVC（.mov）形式で撮影されるのが標準。
- 対応端末をiPhone/Safari系に限定した前提のもと、**サーバー側でのHEVC→H.264変換（トランスコード）は実施しない**。
  - 理由：Safari（iOS/iPadOS/macOS）はHEVCをネイティブ再生可能なため、変換なしでも再生できる。
  - Raspberry Pi 5への変換処理負荷（CPU・処理時間）を避けられるメリットが大きい。
- 前提が崩れた場合（Windows/Android閲覧が必要になった場合）は、この方針を再検討する。

### 2.3 データモデル
- 新規テーブルは作らず、**既存の `Pictures` テーブルを拡張**する。
  - 既存の `mime_type` / `thumbnail_path` / `width` / `height` などのカラムを動画にも流用。
  - 動画の再生時間を保持する `duration` カラム（新規）を追加する想定。
  - コメント・カテゴリ・論理削除／復元・操作ログなど、既存Picturesまわりの仕組みをそのまま動画にも適用できる。

### 2.4 アップロード単位
- 動画は **1回のアップロードにつき1本のみ**。
- 既存の写真複数枚アップロード（最大5枚）とは別フローとする。
  - 理由：処理負荷・実装複雑度を抑えるため。将来的な統合は別途検討。

### 2.5 長さ・ファイルサイズ上限
- **30秒 かつ 上限100MB**。
  - iPhoneの4K撮影（高ビットレート）でも30秒なら収まる余裕を持たせたサイズ。
  - どちらか一方を超えたらアップロード時にエラーとする。

### 2.6 位置情報（GPS）等メタデータの削除
- 写真のEXIF位置情報削除（[docs/requirements.md](./requirements.md) 4.1参照）と方針を合わせ、**動画も位置情報メタデータを削除する**。
- 変換（再エンコード）は行わない方針のため、メタデータのみを軽量に除去する方法で実装する（動画本体の再エンコードは発生させない）。
